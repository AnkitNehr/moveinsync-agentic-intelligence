- (event) Spec run started from two authored sources: docs/problem-statement.md (verbatim hackathon brief) and docs/solution-architecture.md (solution design)
- (direction) User asked the spec to be optimised toward the published evaluation weights: business impact and experience 35, agentic design and cost at scale 20, architecture and code quality 20, functionality 25
- (decision) Slug derived as agentic-mobility-intelligence; input was multi-source so no upstream slug was available to inherit
- (decision) Input judged rich rather than sparse, so the five-field kernel was distilled directly with no elicitation pass
- (decision) Problem framed as five gaps rather than one reporting gap: context, attribution, action, latency, audience. Attribution is the gap the brief is implicitly asking for
- (decision) Core thesis adopted: the LLM never computes a number. Deterministic code owns all arithmetic; the model owns salience, causal explanation, and communication. Chosen because it is simultaneously the cost answer, the correctness answer, and the latency answer
- (decision) Mix-rate variance decomposition selected as the attribution method: separates rate effect (entity got worse) from mix effect (volume shifted toward a weak entity) and sums to the observed delta, so it is auditable
- (decision) Scope laddered L0 to L5. L0-L2 declared must-have and together satisfy every mandatory requirement in the brief; L3-L5 are score-maximising
- (capability) CAP-1 ingest heterogeneous mobility data into one trip-level fact set, retaining incomplete records with quality flags instead of dropping them
- (capability) CAP-2 compute governed metrics from a single versioned catalog so every consumer resolves the identical definition
- (capability) CAP-3 attach four reference points (trend, SLA, peer, industry) to every emitted metric value so no number is presented bare
- (capability) CAP-4 detect statistically unusual metric movements and rank them by whether they deserve human attention
- (capability) CAP-5 attribute a metric movement to the entities that caused it, with contributions summing to the observed delta
- (capability) CAP-6 triage ranked candidates into incidents, clustering related movements and suppressing already-raised or dismissed ones
- (capability) CAP-7 explain a promoted incident with evidence, every quantitative claim traceable to a supplied observation
- (capability) CAP-8 render the same incident or period for three personas differing in framing, depth, and recommended action
- (capability) CAP-9 run the sense-reason-act cycle on a schedule with no human prompting
- (capability) CAP-10 answer natural-language questions by routing to the governed metric layer rather than raw SQL
- (capability) CAP-11 act on an incident and schedule a follow-up check, self-escalating when the metric has not recovered
- (capability) CAP-12 operator console for reviewing incidents, evidence, and attribution, with dismiss and escalate actions
- (capability) CAP-13 report per-run cost and latency so the cost-per-interaction claim is demonstrable rather than asserted
- (constraint) No LLM may compute, derive, or restate a numeric value absent from its structured input. Bends the whole architecture: forces a deterministic metric layer and a post-generation numeric validator
- (constraint) The sample dataset has not been received, so ingest must be driven by a declared column mapping rather than hardcoded field access
- (constraint) LLM calls receive only ranked or aggregated payloads, never raw trip rows. Caps token cost independently of tenant size
- (constraint) Agents reach data only through the metric-layer interface, never direct SQL, so porting onto a real platform is one adapter
- (constraint) Every fact row carries tenant_id and the query layer injects the filter; no query path may omit it
- (constraint) Model tiering is mandatory: triage, routing, and chat intent on the cheap tier; causal reasoning and narrative on the strong tier
- (constraint) Per-tenant token budget is bounded; on exhaustion the system degrades to deterministic alerts rather than going dark
- (constraint) The prototype must run end to end on a laptop from the sample dataset with no cloud infrastructure required
- (constraint) A metric below its declared minimum sample size is returned as insufficient-sample, never as a number
- (decision) Six spec-authored companions created, content-typed: architecture-diagrams.md, metric-catalog.md, agents.md, personas.md, stack.md, evaluation-and-deliverables.md. Diagrams land in a companion per Spec Law rule 2
- (decision) Stack recommendation recorded as Java 21 plus Spring Boot 3, DuckDB over Parquet, Postgres for incident state, Angular console, Claude tiered with prompt caching. Java chosen because criterion 3 rewards deployability into an existing Java platform
- (decision) Python plus Polars recorded as an explicit velocity alternative that trades away part of criterion 3, so the calendar can decide
- (assumption) Dataset shape assumed from the brief description because the file has not been received
- (assumption) Assumed the dataset spans enough history for period-over-period comparison; if it is a single snapshot, trend benchmarking degrades to SLA and peer only
- (assumption) Industry benchmark values assumed to come from static config, since no external benchmark source is provided
- (assumption) Multi-tenancy assumed to be demonstrated structurally on a single-tenant demo rather than proven at scale
- (assumption) Output assumed English-only
- (assumption) Escalations and notifications assumed to be recorded or simulated rather than delivered into real vendor or comms systems
- (question) Which persona is the primary demo target? It decides where the L5 polish budget goes
- (question) What is the actual submission deadline? It decides Java (better scored) versus Python (faster to build)
- (question) Does the dataset carry employee-level roster and shift data? Without it the line-manager persona cannot be served
- (question) Are SLA targets supplied in the dataset or brief, or do we define them ourselves?
- (question) For the demo, is a real delivery channel (Slack, email) available, or should delivery be simulated?
- (question) Does the dataset include a vendor identifier with enough volume per vendor for peer comparison to be meaningful?
